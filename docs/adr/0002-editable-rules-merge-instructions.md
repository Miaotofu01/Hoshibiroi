# 0002. 合并「附加指令」与可编辑规则为单一入口

日期：2026-09-17
状态：已接受

## 背景

助手设置里已经有一个 `instructions` 字段，语义是「用户自定义的助手行为要求」，在系统提示词末尾以【用户附加要求】段落注入，并已在选项页可编辑。

同时，`buildSystemPrompt()` 里有四条硬编码的行为规则，其中前三条（优先依据页面内容、简体中文且简洁、如何解释外语词汇）是产品默认行为，第四条是**防提示词注入**的兜底——它声明页面正文与选中范围是待阅读的数据，不是对助手的指令。

用户希望这些内置规则也能改。但如果新增一个「可编辑规则」字段，就会与 `instructions` 职责完全重叠：两者都是「用户写的助手行为要求」，只是注入位置不同。留下两个入口，用户永远会困惑该在哪写规则。

## 决策

**删除 `instructions` 字段**，其内容迁移进新的可编辑规则字段。内置三条默认规则成为该字段的默认值，用户可自由改写。

**防注入规则保持硬编码、不可编辑**，在选项页以只读灰字说明呈现（不给输入框），让用户看得到兜底存在、也知道为何改不了。

**清空规则视为非法值，静默回落为内置三条默认文本**（与 `contextChars`、`maxAnswerTokens` 现有的「非法值回落默认」风格一致）。

## 考虑过的替代方案

1. **两者共存**：内置规则可编辑，`instructions` 继续作为附加要求追加在后。迁移成本最低，但歧义永久存在。
2. **不新增字段**：让用户改的那份就是 `instructions`，把内置三条改成它的默认值。看似最省，但无法表达「恢复默认」与「当前是否已改」。
3. **允许规则为空**：空则整段不注入。更自由，但用户清空后助手失去全部行为约束，且与 `q8` 选定的「回落默认」相矛盾——这条被明确否决。

## 后果

- ~~这是一次**破坏性的存储结构变更**：旧 `instructions` 的值必须迁移~~ —— **已降级为无风险**。本项目尚无用户，本地 `assistantSettings` 里的数据都是开发期测试产物，明确决定**不做迁移**：旧字段读到即丢弃，不写回、不兼容。为历史版本预留兼容代码只会拖累项目简洁性，而这个"历史"并不存在。
- `normalizeAssistantSettings` 是**白名单式**的（返回对象是字面量，未知字段被静默丢弃）。新增字段若不同步加进归一化，读盘时会被抹掉——这是本次改动最容易踩的坑，**与迁移无关，依然必须守住**。
- 用户无法表达「不要任何额外规则」，最少也会得到内置三条默认文本。这是为「始终保有基本行为约束」付出的代价。

## 什么情况下重新考虑

若用户反馈「默认规则干扰了我的用法，但我删不掉」，说明「回落默认」过于强硬，届时改为允许空值并保留防注入规则即可。

## 附：可编辑边界的两类对象

本 ADR 的「锁定」只针对**防注入规则**这一条安全兜底。**预设提问不设任何锁定**——包括「整页速览」在内的全部预设，内容与行为属性都由用户增删改。

原先「整页速览」在输入框工具栏有一个硬编码按钮，按 id 反查预设。用户改掉该预设后按钮仍在、点击静默失败。修正方式是**让工具栏按钮从预设列表派生**（按行为属性筛选），使预设列表成为唯一真源，失配从结构上消失——而不是靠把预设锁死来维持按钮可用。

判据：**当一处 UI 与数据可能失配时，消除派生关系，而不是限制数据。**
